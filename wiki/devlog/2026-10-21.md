# 2026-10-21 — M4 session 2: the allocation gate

M4 session 2 is the performance half of the milestone. The goal was an
explicit zero-allocation criterion for warm fixed-capacity stepping, a
per-site classification of every remaining allocation, removal of the
in-scope ones, and a representative benchmark across the seven M0 workloads
against Lua on the same host. **M4 remains open**: session 3 is cross-machine
qualification and closeout.

## 1. Criterion first, optimisation second

`wiki/benchmarks/m4-perf.md` was written before any engine change. It defines
steady-state stepping as the bytes allocated around one
`update!(eng, fixed_dt)` (previous-state stamping, `step_simulation!`,
`finalize_step!` including the fever bucket update, and the `steps_run`
bookkeeping), measured warm, single-threaded, trace off, with `GC.gc()` only
outside the measured region. The pass condition is **sum and max both 0**; a
zero median is not a pass. Capacity growth, reset, launch, and observation
(trace/snapshot/export) are measured and reported separately, and every byte
is classified `steady-state`, `capacity growth`, `reset`, or `export-only`.

The criterion is what made the work tractable: it told us when to stop
optimising the things that only happen once per shot, and it is why the
remaining command-path bytes below are reported rather than hidden inside a
mean.

## 2. What was allocating, and what was done about it

Measured with `Base.gc_bytes()` deltas plus `Profile.Allocs` at
`sample_rate = 1.0` (site attribution) and `--track-allocation=user` (line
attribution). Four causes, all behavioural no-ops:

**2.1 The journal payload was a union.**
`GameEvent.fields` was `Union{Dict{String,Any},ContactPayload}`. Because that
union has a non-isbits member, every contact boxed its payload (288 B/event)
and every scalar `get` re-boxed. `julia/PeggleSim/src/event_fields.jl` is a new
concrete `EventFields <: AbstractDict{String,Any}` superset with one typed
`Union{Nothing,T}` slot per payload key, line metadata flattened into
`line_meta_*` (re-materialized as a nested `"line"` object only at the export
and `iterate` boundary), and interned peg-type/peg-shape strings. A cold
`EventFields(::AbstractDict)` constructor keeps the public "arbitrary payload"
API working, putting keys outside the schema into an `extra::Union{Nothing,
Dict}` slot that is `nothing` on every hot path.

**2.2 `in(::String, ::Tuple)` allocates.**
`_contact_can_score` tested `kind in SCORING_CONTACT_KINDS`. `in` over a tuple
of `String`s builds argument tuples through `argtail`/`tail`, which
heap-allocates for non-isbits elements — about 40 B per test, 93 B per step on
mustache 570, ≈269 KB per shot. Replaced by an explicit disjunction over the
same four literals (`_is_scoring_contact_kind`). This single change took
mustache 570 from 253 → 103 B/step.

**2.3 Tracker state stored scalars in `Any` slots.**
`StyleShotTrackers` and `SlideInversionTrackers` were
`Dict{...,Any}`-everywhere and stored `Float64`/`Int`/`Bool` in `Any` slots, so
every `no_contact_time += dt`, every run length, and every per-line impact
record boxed. All tracker maps and per-(ball, line) payloads are now concrete:
`StyleLastImpact`, `StyleSlideRun`, `SlideTrack`, `SlideHitRecord`,
`Dict{Int,Float64}`, `Dict{Int,Int}`, `Dict{Int,Bool}`. The checkpoint
serializer learned the new types and still emits the same JSON shape (the
ready-to-aim boundary has empty tracker maps, which the parser round-trips).

**2.4 `restore!` threw away all capacity every shot.**
`sim.trackers = deepcopy(ckpt.trackers)` meant warmup could never pay off: each
reset created fresh trackers, so every shot re-grew every map and re-created
every run object. `_restore_trackers!` now restores into the live containers,
and `StyleShotTrackers`/`SlideInversionTrackers` carry small reuse pools
(`run_pool`, `award_pool`, `by_line_pool`, `track_pool`, `hits_pool`) that
`reset_shot!` rewinds by index. A warmed repeat of the same aim now hands the
same objects back out. This also cut reset from 27.8 → 25.4 KB (mustache 900)
and 32.2 → 29.7 KB (mustache 570).

Result on the same host and method: mustache 900 304 → 15.0 B/step, mustache
570 3,929 → 21.5, circles_small 119 → 0, lines_rect_annular 455 → 11.1,
annular_dense 133 → 0. Launch is 0 B on every workload. Full accounting and the
remaining-site table live in `wiki/benchmarks/m4-perf.md` §4.

## 3. The bug the sweep caught and the unit tests did not

`_restore_trackers!` initially copied the checkpoint's tracker maps without
resetting the live slide-inversion trackers, so `track` and `line_hits` leaked
from one candidate to the next. A single candidate ran correctly in isolation
but lost its slide style award when it followed another candidate in the same
worker. `make julia-test` (5,616 tests) and the byte-identical trace corpus both
passed; the full-grid sweep parity failed on exactly 5 of 1,801 candidates of
`lines_rect_annular_multi3` (score short by the 5,000-point slide award). The
fix is to `reset_shot!` each sub-tracker before copying. This is the argument
for keeping the full-grid sweep in the gate: it exercises cross-candidate state,
which per-shot fixtures cannot.

corpus and the sweep grid are the check on that claim.

## 5. Performance

Allocation: steady-state stepping is **0 B/step** on `circles_small` and
`annular_dense`; `lines_rect_annular` is 11.1 B/step (2 nonzero steps of 768),
`mustache` 900 is 15.0 (5 of 922) and `mustache` 570 is 21.5 (13 of 1,797).
p50 and p99 are 0 on every row; the residue is command emission and is itemised
with a fix plan in `wiki/benchmarks/m4-perf.md` §4.3. Launch is 0 B everywhere.

Benchmark (same host, stride 20, 91 candidates): Julia T=1 beats single-thread
Lua by 1.3× on `circles_small`, 2.9× on `lines_rect_annular`, 17.0× on
`annular_dense`, 3.5× on `lines_rect_annular_multi3`, 10.0× on
`annular_dense_multi3`; it is 0.6× on `circles_mixed` and 1.0× on
`overhead_static_2p`, where per-candidate fixed cost dominates and LuaJIT is
hard to beat. Scaling to 12 threads gives 1.6–3.6× on the five simulation-heavy
workloads (0.13–0.30 per-thread efficiency, bounded by 91-candidate
granularity). Tracing is observation-only: traced and untraced rows are
byte-identical. Full tables, method and caveats are in
`wiki/benchmarks/m4-perf.md` §3–§6.

## 6. What session 3 should do

1. Close the command-path residue: give `GameplayCommands` a concrete payload
   type (the same refactor the journal got), pool the derived `EventFields` in
   `apply_commands!`, pre-size `run_pool`, and replace the `start_clearing!`
   comprehension with a reused vector. That is ~10 B/step at mustache 570 and
   would take the gate from "2 of 5 probes at 0" to all five.
2. Re-run `scripts/m4_allocation.jl` and require sum **and** max = 0 on all
   five probes, then re-run the seven-workload benchmark to show the residue
   did not move throughput.
3. Cross-machine qualification per
   `wiki/context/cross-platform-qualification.md`, then M4 closeout. M4 stays
   open until then.

# M4 session 3: strict zero and cross-machine qualification

M4 session 3 is the closeout. It re-measured the committed session-2 profile,
replaced the command-path `Dict` payloads with typed records, took the
performance gate to a strict zero on all five probes, re-ran the seven-workload
benchmark, and qualified the validated corpus on a second host. **M4 is
closed.**

## 1. The session-2 profile was stale

`results/m4/allocation-profile.json` as committed in session 2 was captured at
`git_head=b8e94f0` with `dirty=true`, on a pre-final tree. It does not
reproduce at clean `6544414`: re-measured there, `annular_dense` allocates
~6.3 B/step and fails the gate, and only `circles_small` is genuinely at zero.
The root cause is recorded in `wiki/benchmarks/m4-perf.md` §4.5: the final
session-2 change removed an unsound slide-run map pool, which moved map
creation into the per-bounce path after the profile was captured.

The consequence is narrow: session 2's claim that the gate "passes on
`circles_small` and `annular_dense`" was true only for `circles_small` at its
own commit. The criterion, the method, and the four removed causes stand; the
committed profile's second zero did not. Session 3 re-measured before changing
code, so both columns in `m4-perf.md` §4.1 describe the same tree history.

## 2. The refactor: moving the ownership boundary

Commands are exported to Lua and used to be deep-copied into a
`Dict{String,Any}` at push time. The refactor moves the ownership boundary
rather than deleting it: `GameplayCommands.commands` and `.applied` are now
`Vector{GameplayCommand}`, a concrete
`GameplayCommand <: AbstractDict{String,Any}` record with the envelope
(`type`, `step`, `shot_id`, `sequence`) and one typed slot per emitted payload
key. `push_command!` still detaches caller-owned dictionary input, and the
detached `Dict{String,Any}` is materialized only at the export/snapshot
boundary (`command_snapshot`, `applied_snapshot`, and the trace step record).
The exported key set, value types and ordering are unchanged, so trace bytes
are unchanged. The test that pinned `commands.commands[1]["line"] isa Dict`
was relocated to the export boundary, not weakened.

The reusable pieces:

- event payload views: derived `style_awarded` / `slide_peg_removed` events
  are built from typed command slots instead of reading `Any` from a `Dict`,
  so `emit_derived!` stays unboxed;
- `StyleInfo` callback view: `on_style_shot` receives `eng.style_info`, a
  mutable struct filled in place, instead of a fresh detached `Dict` per call;
- pooled clear queue with insertion sort: `start_clearing!` fills
  `eng.clear_lit` and sorts it in place with `InsertionSort` (stable,
  allocation-free);
- spawn-ball pool: power spawns recycle `BallState` objects from
  `eng.spawn_pool`;
- per-ball slide-run map cache: a ball holds either a live map in
  `slide_runs` or a zeroed one in `slide_cache`, and `reset_shot!` reclaims
  live maps; `run_pool` is monotonic and deliberately not rewound;
- pooled `peg_ids` scratch: `remove_slide_pegs` pushes from per-buffer pooled
  vectors rewound per step.

The per-site table is `m4-perf.md` §4.3.

## 3. The result: strict zero

All five probes are 0.000 B/step with max single-step delta 0, and
`Profile.Allocs` reports zero sites (`sites` is empty, not filtered). The
before/after table is `m4-perf.md` §4.1; the session-2 commit `6544414`
allocated up to 27.1 B/step at mustache 570. Reset bytes are unchanged and
remain reported separately. The six traced fixtures stay byte-identical, and
`make julia-test` is 5,617/5,617: the representation test moved to the export
boundary and gained one detach assertion, so the count is +1, not a weakened
gate. No authoritative value, ordering, or trace byte changed.

## 4. Benchmark re-run

The seven M0 workloads were re-run on the final tree at stride 20 (91
candidates), the same protocol as `m4-perf.md` §3. The two rows watched were
`circles_mixed` and `overhead_static_2p`: the known Julia-slower workload and
the small-workload overhead probe, where a command-path refactor that moves
work to the export boundary would show a fixed-cost change first. The refactor
changes no authoritative work; the run is the control.

The re-run is 7/7 workloads, 0 failed runs, 35/35 thread rows
`serial_parallel_identical = true`, Lua stride-20 agreement clean on all seven,
and full-grid parity clean. Serial-pass throughput delta median is -2.5% (range
-16.2% on the ~20 ms `circles_small` pass, i.e. timing noise, to -0.0%);
parallel-pass per-workload medians span -4.8%…+7.1%. There is no systematic
throughput change and no improvement is claimed.

The two watched ratios moved slightly: `circles_mixed` same-core Julia/Lua
0.641 → 0.692 (still below Lua) and `overhead_static_2p` 1.049 → 0.976 (just
under 1.0×). These are the report's own indicative, not benchmark-grade,
ratios. Tracing is observation-only: untraced 2,212.7 → 2,906.7 c/s and traced
452.3 → 348.5 c/s (ratio 0.2044 → 0.1199), but the traced and untraced rows are
identical, with the same row SHA-256 `ea7c1a2f…` as session 2. Per-candidate
allocation fell on all seven workloads (`lines_rect_annular_multi3` 30,318 →
22,790 B/candidate mean, -24.8%), informational and not the §1.1 gate.
