  14.5/24 = 0.604).
- **Colors are non-gating.** `type_counts = blue 73 / green 1 / purple 0 /
  red 25`; the engine reassigns colors from the seeded pool. No authored
  purple and no color-matched permutation.
- **Smooth rendering.** `Peg.new_annular` gained an optional 8th `segments`
  argument; the 46 ribbon pieces use 16. The default path is byte-identical
  (mustache re-export unchanged, engine suite 480 passed).
- **Playable seams.** An adaptive per-seam angular inset (cap 0.02 rad,
  mean 0.006758) clears cap overlaps; `check_level` is 0 ERROR / 0 WARN.

## Correction: single continuous slides (v3)

**2026-10-22, 17:13 CEST.** The user rejected v2's 46-brick representation:
the ribbons still looked like a bunch of distinct pegs. The requirement is
explicit:

> each ribbon must be a single slide, a single curve that contains all the
> pegs, as in the squiggly circle level.

### What changed

- **Five continuous lines.** Each ribbon is now exactly one `Path.new` (10
  cubic Hermite segments, open; native in the geometry, affine-mapped to
  world in the level) followed by one `Lines.generate` zero-gap annular line:
  `wave_1`..`wave_5`. This is the same primitive as
  [squiggly_circle.lua](../../../peggle_evolved/src/levels/squiggly_circle.lua)
  and [mustache.lua](../../../peggle_evolved/src/levels/mustache.lua); no new
  slide entity was needed.
- **Zero-gap metadata.** 114 generated annular pegs: counts 20/20/26/28/20.
  Every one has `line.gap = 0`, `line.closed = false`, contiguous
  `line.index` 1..count, and `shape.segments = 16`. The 53 circles carry no
  line; total is 167 pegs. The level now contains zero direct
  `Peg.new_annular` calls and no adaptive seam inset.
- **Engine.** [src/systems/lines.lua](../../../peggle_evolved/src/systems/lines.lua)
  accepts optional `spec.peg.segments` for annular lines and forwards it to
  `Peg.new_annular`; `nil` preserves the historical heuristic.
  `Peg.new_annular` itself is unchanged in v3. Level authoring uses
  `segments = 16`, `curve_tolerance = 1.0`, `max_length = 40.0`, `gap = 0`.
- **Path model.** `cubic-hermite-lsq-spline-v1`, 10 cubic Hermite segments per
  ribbon, 8 px end trim, LSQ knot spacing 35 px (wave_2 60 px). Fit RMS
  0.356/1.798/0.315/0.325/0.225 px; max 1.284/7.306/1.146/1.125/0.828 px;
  min curvature radius 30.16/27.66/73.78/72.80/52.32 px (native).
- **Counts.** Authored `type_counts = red 25 / green 1 / purple 0`; blue
  derived 141. `check_level` reports 167 pegs (53 circles, 114 annular),
  ERRORS 0, WARNINGS 0, PASS.
- **Fixtures.** bench, one ball, `fell_out`: `center` aim 900, 312 steps,
  21 pegs, 13,860 pts, no style; `left_wall` aim 1800, 658 steps, 20 pegs,
  7,600 pts, no style; `ribbon` aim 120, 434 steps, 41 pegs, 47,640 pts,
  `slide` x1. The `ribbon` shot can now award SLIDE because line metadata is
  present (v2 could not).

## Terminal-sector repair (v4)

**2026-10-22, late evening.** The user rejected v3 as well: the ribbon looks
**inflected near its ends** — the slope bends one way and then the other in the
last few pegs, instead of continuing into a clean end. They also restated the
end-face contract: the ribbon is a chain of **annular sectors** (two arc sides +
two flat radial sides), so the terminal face is the **last sector's natural
radial side**, flat and sharp, and it is just another peg in the line.

A first experiment (never committed, kept as a negative example in
`temp/ribbon_waves_v4_wrong.patch`) misread the complaint as an end-face
problem: it trimmed the body and glued a separate **180-degree semicircular
`Peg.new_annular` cap** (r_in = 0) onto each end, line-less, shifted 0.02 px
outward. That is not an annular sector, adds a seam and a gap, drops the end
out of the line, and does not remove the path inflection. It also churned the
whole corpus. Rejected and reverted.

### Root cause

The defect is in the **centerline fed to `Lines.generate`**, not in the end
face. The pinned `cubic-hermite-lsq-spline-v1` fit estimates its first/last
cubic tangents from an asymmetric, rounded-end-biased neighbourhood (the source
centreline is a per-column silhouette midpoint and the reference ends are
rounded brick ends). The fitted terminal cubics are therefore S-shaped: the
curvature changes sign inside the cubic and the tip curvature is 3-8x the
body's (`wave_1` end: -0.0016 -> +0.0335). `Lines.generate` tessellates that
curve into sub-half-thickness hooks (centreline radius 18-32 world px against a
20-21 px band, `r_in` 8-10 world px). That pinch/hook is the visible
"inflection".

### Fix (generator-side; the pinned geometry is unchanged)

Each ribbon's first and last cubic is replaced by **the circular arc through
the same two endpoints that is tangent to the path at the interior knot**
(standard arc-to-Bezier conversion, still one cubic):

- constant, single-signed terminal curvature — no internal inflection;
- C1 with the rest of the line;
- exact terminal endpoint, so the line extent does not move;
- the exposed radial side of the last sector is the **flat end face**, sharp
  corners, nothing added beyond it;
- no cap peg, no pie/semicircle, no rounding, no extra geometry;
- the terminal sector is a normal line peg (metadata/count/slide intact).

The emitted path differs from the pinned `ribbons[].path` only in those two
cubics (<= 1.387 world px). `load_geometry` gates the repair on 201 samples per
terminal cubic: sign change, non-constant curvature, moved endpoint or C1 break
fails the build. `--check-geometry` runs only that gate and is part of the
capture script in both modes.

### Results

  endpoint arc is almost flat; no sector is tighter than twice the band
  thickness. The old hooks were 18-32 world px with `r_in` 8-10.
- **Counts:** 161 pegs = 53 circles + 108 annular, lines **20/20/24/24/20**
  (was 167 / 114 / 20/20/26/28/20). The repair removes the over-tessellation
  the hooks forced (a hooked cubic had to split into four pegs; its arc fits as

- **Mask:** cleaned IoU **0.939040** (P 0.961875, R 0.975342); bands
  0.922524 / 0.877815 / 0.913658 / 0.907752 / 0.917864; raw 0.926712. About
